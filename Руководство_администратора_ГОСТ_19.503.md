## 1. Общие сведения о системе

ИС «Яга» предназначена для автоматизации учёта, обработки и анализа данных в ИТ-командах, бизнес-подразделениях, управлении проектами.

**Основные функции системы:**

- управление проектами;
- управление задачами;
- контроль прогресса выполнения задач;
- разграничение прав доступа пользователей.

ИС «Яга» рассчитана на работу операторов, администраторов и конечных пользователей с базовой компьютерной подготовкой.

---

## 2. Структура системы

ИС «Яга» состоит из следующих основных компонентов:

- **Веб-приложение** — основной интерфейс пользователей.
- **Серверная логика и API** — бизнес-логика, управление задачами, проектами, базой знаний.
- **СУБД** — хранение данных задач, статей, пользователей, логов.
- **Хранилище файлов** — прикреплённые файлы, вложения, выгрузки.
- **Сервисы аутентификации и авторизации** — интеграция с корпоративными каталогами (LDAP/AD) и провайдерами идентификации (SAML, OIDC).
- **Сервис уведомлений** — почта, мессенджеры.

## 3. Настройка и проверка системы

### 3.1. Подготовка среды

- Проверить соответствие аппаратных и сетевых требований.
- Подготовить учётные записи и сертификаты для установки.
- Настроить правила межсетевых экранов и балансировщики нагрузки.
- Подготовить СУБД и хранилище файлов.

### 3.2. Установка компонентов

- Развернуть серверную часть (через инсталлятор/Docker/Kubernetes).
- Настроить параметры подключения к СУБД и хранилищу файлов.
- Импортировать начальные данные (справочники, роли, базовые пространства базы знаний).
- Настроить сертификаты HTTPS и домен.
- Запустить сервисы и проверить доступность веб-интерфейса.

### 3.3. Первоначальная конфигурация

- Создать учётную запись администратора.
- Настроить интеграцию с корпоративным каталогом пользователей (LDAP/AD).
- Определить политики паролей и блокировки учётных записей.
- Настроить базовые пространства базы знаний и шаблоны статей.
- Настроить шаблоны задач и доски (Kanban) для типовых процессов.

### 3.4. Проверка системы

**Порядок действий при обновлении системы:**

- Ознакомиться с заметками к релизу и списком изменений.
- Выполнить резервное копирование.
- Провести обновление в нерабочее время.
- Применять обновления строго по инструкции поставщика.
- После обновления проверить работоспособность основных функций.

**При выявлении критических ошибок:**

- Остановить обновлённые сервисы.
- Восстановить данные из резервной копии.
- Запустить предыдущую версию.

### 3.5. Резервное копирование и восстановление

**Регулярное резервное копирование — критически важно для сохранности данных.**

**Что копировать:**

- Базу данных (полный дамп через `pg_dump` или снапшот СУБД);
- Хранилище файлов (вложения, изображения, экспорты);
- Конфигурационные файлы (параметры подключения, сертификаты, настройки интеграций).

**Частота:**

| Тип | Периодичность | Хранение |
|---|---|---|
| Полное копирование БД | Ежедневно | 30 дней |
| Инкрементальное копирование | Каждый час | 24 часа |
- Архив хранилища файлов | Ежедневно | 30 дней |
- Копирование конфигурации | При каждом изменении | Бессрочно |

**Процедура восстановления:**

1. Остановить сервисы ИС.
2. Восстановить БД из дампа (`pg_restore` или восстановление снапшота).
3. Восстановить хранилище файлов из архива.
4. Восстановить конфигурационные файлы.
5. Запустить сервисы и проверить целостность данных.

### 3.6. Мониторинг системы

**Ключевые метрики для мониторинга:**

| Метрика | Норма | Действие при отклонении |
|---|---|---|
| Доступность веб-интерфейса | 99.9% | Проверить статус сервисов, перезапустить |
| Время ответа API | < 500 мс | Проверить нагрузку, индексы БД, кэш |
| Использование ОЗУ сервера | < 80% | Увеличить ресурсы или оптимизировать |
| Использование диска | < 85% | Очистить логи, увеличить объём |
| Количество активных сессий | По лицензии | Проверить лицензию, отключить неактивных |

**Инструменты мониторинга:**

- Встроенная панель «О системе» — общее состояние, версия, количество пользователей.
- Логи приложения — `/var/log/yaga/` (уровни DEBUG, INFO, WARN, ERROR).
- Внешние системы — Prometheus + Grafana, Zabbix (при интеграции).

### 3.7. Управление пользователями и ролями

**Создание пользователя:**

1. Перейти в «Настройки» → «Управление пользователями».
2. Нажать «Создать пользователя».
3. Заполнить: ФИО, email, роль, пространство (по умолчанию).
4. Нажать «Сохранить». Пользователь получит приглашение на email.

**Роли в системе:**

| Роль | Права |
|---|---|
| Администратор | Полный доступ ко всем настройкам, пользователям, пространствам |
| Руководитель пространства | Создание/удаление задач, управление командой, настройки пространства |
| Исполнитель | Работа с назначенными задачами, создание статей, комментарии |
| Наблюдатель | Просмотр задач и статей без права редактирования |

**Блокировка и удаление:**

- Блокировка — пользователь сохраняется в системе, но не может войти. Используется для временного отстранения.
- Удаление — необратимое действие. Задачи и статьи удалённого пользователя сохраняются, автор помечается как «Удалённый пользователь».

## 4. Сообщения администратору

| Сообщение / событие | Возможные причины | Рекомендуемые действия |
|---|---|---|
| «Сервис недоступен» | Остановка сервиса, перегрузка, сетевые проблемы | Проверить статус сервисов, логи, нагрузку; перезапустить при необходимости |

## 5. Обеспечение информационной безопасности

### 5.1. Аутентификация и парольная политика

- Минимальная длина пароля — 12 символов.
- Требование к сложности: заглавные и строчные буквы, цифры, спецсимволы.
- Срок действия пароля — 90 дней (настраивается).
- Блокировка после 5 неудачных попыток входа на 15 минут.
- Поддержка двухфакторной аутентификации (TOTP, SMS).

### 5.2. Защита данных

- Все подключения — через HTTPS (TLS 1.2+).
- Пароли хранятся в виде хэшей (bcrypt / Argon2).
- Резервные копии шифруются при хранении.
- Журнал аудита — все действия пользователей с задачами, статьями и настройками фиксируются с указанием времени, IP-адреса и типа действия.

### 5.3. Сетевая безопасность

- Размещение серверов в изолированном сегменте сети.
- Доступ к БД только с серверов приложения.
- Ограничение доступа к API по IP-адресам (whitelist).
- Регулярное обновление ОС и зависимостей (security patches).

### 5.4. Управление доступом

- Принцип минимальных привилегий — каждому пользователю назначается только необходимая роль.
- Периодическая проверка прав доступа (раз в квартал).
- Отзыв доступа при увольнении/переводе сотрудника — в день прекращения работы.
